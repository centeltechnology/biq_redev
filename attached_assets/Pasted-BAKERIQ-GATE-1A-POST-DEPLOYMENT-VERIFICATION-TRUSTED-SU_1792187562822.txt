BAKERIQ — GATE 1A
POST-DEPLOYMENT VERIFICATION & TRUSTED SUBSCRIPTION SYNC

BACKGROUND

The combined security release has now been published.

It contains:
1. Stripe Connect webhook signature verification.
2. Fail-closed containment of the legacy subscription endpoint.

The pre-deployment security suite passed 38 tests.
The production build passed.
The owner personally verified the Stripe Connect
signing secret against the correct live Stripe endpoint.

The architecture audit also identified a separate problem:

Stripe billing data is synchronized into managed Stripe
tables, but BakerIQ feature access and platform fees
depend on bakers.plan.

There is no confirmed, reliable synchronization path
connecting verified Stripe subscription events to
BakerIQ's own account entitlements.

We need to finish Gate 1A.

IMPORTANT:

There are currently two Pro accounts without Stripe
subscriptions. The owner confirms BOTH are intentional
test accounts, including the super-admin account.

Preserve their access.
Do not classify them as paying subscribers.
Do not automatically downgrade them.

No existing subscription prices or platform fees
should change.

==================================================
PHASE 2 — IMPLEMENT VERIFIED SUBSCRIPTION SYNC
==================================================

Implement a reliable server-side bridge between
verified Stripe subscription information and
BakerIQ account entitlements.

Reuse the existing managed Stripe integration wherever
possible.

Do not create a second competing webhook system.

The intended architecture is:

Stripe billing events
    ↓
Verified managed Stripe integration
    ↓
Authoritative subscription status
    ↓
BakerIQ subscription synchronization
    ↓
Correct baker plan and platform-fee entitlement


REQUIREMENTS

1. Only trusted server-side Stripe data may authorize
   changes to a baker's subscription entitlements.

2. Never trust client-submitted plan names, status
   strings, customer IDs, or subscription IDs as
   authorization to upgrade an account.

3. Verify the association between the Stripe customer,
   subscription, Checkout session, and BakerIQ baker.

4. Use the configured Stripe Price IDs to determine
   Basic versus Pro.

5. Preserve existing plan definitions:

   FREE: $0/month, 7% platform fee
   BASIC: $4.99/month, 5% platform fee
   PRO: $9.99/month, 3% platform fee

6. Support subscription lifecycle events:

   - New paid subscription
   - Upgrade
   - Downgrade
   - Renewal
   - Trial where applicable
   - Failed payment
   - Past-due subscription
   - Cancellation scheduled for period end
   - Immediate cancellation
   - Expired subscription

7. Use a clearly defined entitlement policy.
   Preserve paid access through an already-paid period
   when applicable.

   If cancellation, grace-period, or past-due policies
   are ambiguous, identify the decision rather than
   silently imposing a new policy.

8. Make processing idempotent.

   Duplicate or delayed Stripe events must not cause
   duplicate subscription effects or regress account
   state to an older status.

9. Use authoritative event data and, where appropriate,
   retrieve current subscription state directly from
   Stripe before updating local access.

10. Keep subscription synchronization independent of
    whether the baker has an active browser session.

11. Include a safe reconciliation mechanism for missed
    or delayed events, with bounded retries, failure
    visibility, and no uncontrolled concurrent updates.

12. Never restore the unauthenticated legacy callback.

==================================================

affiliate commission and referral-credit operations.

Inspect those business rules and preserve the ability
to process legitimate awards through a trusted path.

Requirements:

- Awards must be based on verified qualifying activity.
- Never trust arbitrary client-submitted paid status.
- Prevent duplicate awards.
- Preserve existing referral and affiliate relationships.
- Preserve historical records.
- Do not issue real payouts or historical adjustments.
- Do not invent new commission percentages or rules.

If a qualifying billing event or existing award rule
cannot be established safely, isolate that portion
and report the blocker without fabricating awards.

Do not silently discard legitimate existing rules.
