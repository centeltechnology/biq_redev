BAKERIQ — ARCHITECTURE & FEATURE DISCOVERY AUDIT

We are preparing a significant UX and product-experience
improvement for BakerIQ.

DO NOT IMPLEMENT ANY CHANGES YET.

This is a READ-ONLY discovery and documentation task.

Do not modify application code, database schemas,
production data, billing configurations, or existing
user accounts.

Do not install packages or run migrations.

Do not expose secrets, credentials, API keys, or
sensitive customer information.

I need you to inspect the EXISTING application and
provide a factual report of its current capabilities,
architecture, data models, and limitations.

We are planning to make BakerIQ easier for beginners
while retaining all functionality for experienced bakers.

The goal is to reuse existing functionality wherever
possible rather than rebuild working systems.


=============================================
1. APPLICATION ARCHITECTURE
=============================================

Identify:

- Frontend framework and routing structure
- Backend framework
- Database and ORM
- Authentication and authorization
- Account/tenant architecture
- Existing analytics and event tracking
- Background jobs and scheduled processes
- Email/notification infrastructure
- File/image storage
- Stripe integration architecture
- Existing automated tests

Identify major application modules and their
responsibilities.

Explain how bakery accounts, their users,
customers, products, prices, requests, quotes,
orders, and payments are related.

Identify areas of tight coupling that could
complicate changes.

Do not recommend a new technology stack unless
there is a demonstrated technical necessity.


=============================================
2. SIGNUP & ONBOARDING
=============================================

Inspect the complete account creation and
seven-step onboarding process.

Document:

- What information each step collects
- Which fields are required
- Which fields are optional
- How progress is saved
- Whether onboarding can be resumed
- Whether completed steps can be revisited
- What happens when onboarding is skipped
- What records are created during signup
- What records are created during onboarding
- How starter pricing is generated
- How bakery URLs are assigned
- When order pages become publicly accessible
- How Stripe onboarding is triggered
- How onboarding completion is determined

IMPORTANT:

Determine whether onboarding can support
different experiences without creating
separate account systems.

We are considering three presentation modes:

GUIDED
- Simplified initial dashboard
- Recommended next actions
- Less visual complexity

FOCUSED
- User selects a specific goal
- Interface emphasizes related tools

FULL
- Existing complete dashboard and navigation
- No mandatory tutorials

All users must retain access to features allowed
by their subscriptions.

Determine what existing architecture could
support this approach.

Do not implement it.


=============================================
3. PRICING SYSTEM
=============================================

This is especially important.

Inspect ALL existing pricing functionality:

A. Product/menu pricing

- Cake sizes
- Serving counts
- Cake shapes
- Flavors
- Frostings
- Decorations
- Add-ons
- Treat products
- Delivery/setup prices
- Pricing presets
- Custom pricing options

B. Cost-based pricing calculator

- Material costs
- Labor hours
- Hourly labor rate
- Overhead percentage
- Profit calculation
- Suggested selling price
- Saved calculations
- Express Item integration

C. Customer-facing price calculations

- Custom cake estimates
- Multi-tier calculations
- Treat quantities
- Add-ons
- Taxes
- Delivery charges
- Quote adjustments

Determine:

1. Whether these systems share pricing logic.
2. Whether calculations can produce inconsistent
   results across screens.
3. How profit margin is actually calculated.
4. Whether the suggested price includes a separate
   profit target or only cost plus overhead.
5. Whether default prices are editable.
6. Whether prices must be explicitly reviewed
   before publishing.
7. Whether an existing saved calculation can be
   turned into a quote or Express Item.
8. Whether cost-calculator values can be passed
   between screens without reentry.

Also investigate whether any AI-powered pricing
recommendation functionality exists.

Look for:

- AI pricing suggestions
- AI-assisted quote pricing
- Market-based starting prices
- AI recommendations during onboarding
- AI pricing APIs or service modules

Clearly distinguish:

IMPLEMENTED AND ACTIVE
IMPLEMENTED BUT UNUSED
PARTIALLY IMPLEMENTED
NOT IMPLEMENTED

Do not infer AI functionality simply because
the application has pricing presets.

=============================================
6. REQUEST TO QUOTE TO ORDER
=============================================

Trace the COMPLETE lifecycle:

Customer submits request
→ Baker receives request
→ Baker reviews details
→ Prepared quote is generated
→ Baker edits pricing if needed
→ Baker saves draft
→ Baker sends quote
→ Customer accepts or declines
→ Order is confirmed
→ Deposit/payment is handled
→ Order appears in business records

Document:

- Actual existing statuses and transitions
- Which actions are automatic
- Which actions require baker approval
- Whether creating a quote sends an email
- Whether sending a quote requires Stripe
- Whether accepting a quote creates an order
- Whether payments are required to confirm orders
- How manual/offline payments work
- How customers are associated with requests
- How duplicate customers are handled
- How notifications are sent

Identify any ambiguous or inconsistent states.

Distinguish what the current code ACTUALLY does
from what the UI appears to suggest.
